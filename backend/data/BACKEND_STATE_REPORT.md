# Backend State Report & Transformation Plan

**Date:** December 11, 2025
**Status:** Static / Prototype Phase
**Target:** Dynamic, User-Centric AI Application

---

## 1. Current State of the Backend

### Architecture
- **Framework:** Python FastAPI
- **Entry Point:** `backend/main.py`
- **Core Logic:** Modularized in `backend/core/` (Phase 1: Data Processing, Phase 2: Simulation, Phase 3: Maintenance).

### Data Handling (The "Static" Problem)
Currently, the backend is **not** reading live user data. It relies entirely on static CSV files loaded into memory at startup:
- **PV Data:** `backend/data/processed_pv_data_2023_2024.csv`
- **Consumption Data:** `backend/data/processed_power_usage_2023_2024.csv`

When the `/simulate` endpoint is called, it uses this global, pre-loaded dataset. This means every user sees the same simulation based on the same historical data, regardless of who is logged in.

### AI Models
- **Primary Model:** XGBoost (`backend/models/production_xgboost.pkl`)
- **Baseline Model:** SARIMA (`backend/models/sarima_lr_baseline.pkl`)
- **Feature Engineering:** Handled by `backend/core/phase_1/data_processing.py`.
- **Training:** Manual execution of `src_final/train_and_save_production_model.py`.

### Supabase Connection
- **Frontend:** Connected via `lib/supabase.js`. Used successfully for **Authentication** (Sign Up/Login).
- **Backend:** **No direct connection.** The Python backend does not communicate with Supabase. It receives data only via API requests from the frontend or reads local files.

## 2. Next Steps for Effective Data Reading

To transform this from a static demo to a real application, we must move from **File-Based** to **Database-Based** architecture.

### Step 1: Database Schema (Supabase)
Create the following tables in Supabase to store user-specific data:

```sql
-- Stores raw PV generation data uploaded by users
create table pv_readings (
  id bigint generated by default as identity primary key,
  user_id uuid references auth.users not null,
  timestamp timestamptz not null,
  production_kwh float not null,
  created_at timestamptz default now()
);

-- Stores household consumption data
create table consumption_logs (
  id bigint generated by default as identity primary key,
  user_id uuid references auth.users not null,
  timestamp timestamptz not null,
  consumption_kwh float not null,
  created_at timestamptz default now()
);

-- Stores model metadata per user (if personalized models are needed)
create table user_models (
  user_id uuid references auth.users primary key,
  model_path text, -- Path to model file in Supabase Storage
  last_trained timestamptz,
  accuracy_score float
);
```

### Step 2: Backend Integration
1.  **Install Supabase Client:** Add `supabase` to `backend/requirements.txt`.
2.  **Initialize Client:** Create `backend/db/client.py` to initialize the Supabase Python client using service role keys.
3.  **Update Endpoints:** Modify `/simulate` to accept a `user_id` (or token), fetch that specific user's data from `pv_readings` and `consumption_logs`, and run the simulation on *that* data.

## 3. AI Model Continuous Learning (The "Smart" Aspect)

To make the AI model "always read new user data," we need an automated pipeline.

### The Pipeline
1.  **Data Ingestion:** User uploads a CSV via the frontend.
2.  **Storage:** Frontend parses CSV and inserts rows into Supabase `pv_readings`.
3.  **Trigger:** A background task or a specific API endpoint (`/retrain`) is called.
4.  **Retraining Process:**
    -   Fetch all historical data for `user_id` from Supabase.
    -   Preprocess data (clean, feature engineering) using `backend/core/phase_1`.
    -   Train a **new** XGBoost model specific to that user (or fine-tune a global model).
    -   Save the model artifact (e.g., `user_123_model.pkl`) to Supabase Storage or local disk.
5.  **Inference:** When the user requests a prediction, load *their* specific model.

### Implementation Plan
-   **New Endpoint:** `POST /api/v1/models/retrain`
    -   Input: `user_id`
    -   Action: Triggers the training script programmatically.
-   **Model Registry:** Keep track of which model belongs to which user in the `user_models` table.

## 6. Critical Context & Strategic Priorities

### Key Code Files
The most important files to understand the current implementation:
- `backend/main.py`: Current endpoint structure and API entry point.
- `backend/core/phase_1/data_processing.py`: The data loading and feature engineering logic.
- `lib/services/pythonApi.js`: Frontend-backend communication layer.
- `pages/predictions/index.jsx`: Current UI implementation for predictions.

### Current Pain Points
The immediate blockers preventing this from being a real product:
1.  **Static Data:** Users cannot upload their own data; everyone sees the same hardcoded simulation.
2.  **No Database Link:** The backend is isolated from Supabase, preventing persistent user state.
3.  **Manual Training:** Model updates require manual script execution, not automated by user activity.

### Strategic Priorities (Decision Matrix)
To move forward, the team must choose a focus. **Recommendation: Option A**.

*   **[RECOMMENDED] A. Get real user data flowing (Upload CSV → Supabase → Backend)**
    *   *Why:* This is the foundation. Without user data, the AI has nothing relevant to predict.
*   **B. Implement the Gemini hybrid approach for AI advice**
    *   *Why:* Adds "flashy" features, but useless if the underlying data is fake.
*   **C. Build the auto-retrain pipeline**
    *   *Why:* Essential for long-term accuracy, but needs data flow (Option A) first.
